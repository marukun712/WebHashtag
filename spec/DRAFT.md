# WebHashtag

**Draft 0.1**

---

## 概要

WebHashtagは、ハッシュタグの仕組みをWeb全体に応用するプロトコルです。
プラットフォームの協力を必要とせず、どんなWebページでもタグサーバーへのリンクを貼るだけでタグに参加できます。

---

## 登場人物

### タグサーバー (Tag Server)

ハッシュタグを管理し、各タグに登録された記事一覧を保持するサーバーです。

- タグURLは `{サーバー}/tag/{タグ名}` の形式に従います
  - 例: `tag.example.com/tag/typescript`
- タグ名に使用できる文字は `[a-zA-Z0-9_-]+` です
- タグサーバーは**ヘッドレス**です — UIではなく機械可読なAPIを公開します
- 同じタグ名を持つタグサーバーが複数存在してもかまいません

### コンテンツサーバー (Content Server)

個人ブログ、プラットフォームの投稿、その他あらゆる公開WebページがContent Serverになれます。

**特別なセットアップは不要です。** 記事ページにタグサーバーへのリンクが含まれていれば、それだけで参加できます。

---

## 登録フロー

1. 著者が記事にタグサーバーへのリンクを追加します:
   ```html
   <a href="https://tag.example.com/tag/typescript?url=https://blog.example.org/posts/ts-tips">#TypeScript</a>
   ```
2. 著者 (または訪問者) がそのリンクを一度クリックします。
3. タグサーバーが `url` クエリパラメーターから記事URLを取得します。
4. タグサーバーはリクエストされたタグ名が `tags` リストに含まれているかを確認します。含まれていない場合は `404` を返し、処理を中断します。
5. タグサーバーが記事URLを取得 (**バック検証**) し、そのHTMLにタグリンクが存在することを確認します。
6. 確認できれば、記事をタグに登録します。

この仕組みにより、**ページのオーナーだけが自分のコンテンツを登録できます** — 第三者は他人のページのHTMLを操作できないため、勝手にタグ付けすることができません。

---

## 分散について

タグサーバーは互いに独立しており、フェデレーションは不要です。

複数のタグサーバーに登録したい場合、著者は複数のリンクを記事に含めるだけです。

```html
<a href="https://tag.example.com/tag/typescript">#TypeScript</a>
<a href="https://tag.example.net/tag/typescript">#TypeScript</a>
```

アグリゲーターは各タグサーバーのAPIを個別に叩くことで、複数サーバーをまたいだ記事収集ができます。

---

## タグサーバーAPI

タグサーバーは以下のエンドポイントを公開する必要があります:

```
GET /tag/{タグ名}?url={記事URL}   — 登録トリガー (記事からリンクされるURL)
GET /tag/{タグ名}.json            — 記事一覧 (JSON)
GET /feed/{タグ名}.atom           — 記事一覧 (Atomフィード)
```

`/tag/{タグ名}` は記事に埋め込まれるリンクのURLであり、クリックされることで登録フローが開始されます。`url` パラメーターには登録対象の記事URLを指定します。データ取得には `.json` または `.atom` を使用します。

### JSONレスポンス形式

バック検証の際にOGPメタデータが取得できた場合、タグサーバーはその情報を記録・返却することが**推奨**されます。

```json
{
  "tag": "typescript",
  "server": "tag.example.com",
  "entries": [
    {
      "url": "https://blog.example.org/posts/ts-tips",
      "registeredAt": "2026-06-02T12:00:00Z",
      "ogp": {
        "title": "TypeScriptの型システム入門",
        "description": "TypeScriptの型システムについて解説します。",
        "image": "https://blog.example.org/posts/ts-tips/ogp.png"
      }
    }
  ]
}
```

### サーバーメタデータ

タグサーバーは以下のパスにメタデータファイルを公開する必要があります。

```
GET /.well-known/webhashtag.json
```

```json
{
  "version": "0.1",
  "name": "Example Tag Server",
  "mode": "open",
  "publicKey": null,
  "tags": ["typescript", "javascript", "rust", "go", "python"]
}
```

`mode` は `"open"`(誰でも登録可能)または `"closed"`(署名済みトークンが必要)のいずれかです。

#### `tags` フィールド

`tags` はこのサーバーが受け付けるタグ名の配列です。

- 配列として宣言された場合、リストに含まれないタグ名への登録リクエストは `404` を返します
- タグ名はすべて既存の命名規則 (`[a-zA-Z0-9_-]+`) に従わなければなりません。

**`tags` の宣言例**

```json
{
  "version": "0.1",
  "name": "Programming Tag Server",
  "mode": "open",
  "publicKey": null,
  "tags": ["typescript", "javascript", "rust", "go", "python", "react", "nodejs"]
}
```

## 認証 (クローズドタグサーバー)

クローズドタグサーバーは、認証済みユーザーのみに登録を制限します。仲間内や組織内での限定的な運用に適しています。

### 鍵の公開

タグサーバーはEd25519公開鍵を `/.well-known/webhashtag.json` に公開します:

```json
{
  "mode": "closed",
  "publicKey": "<base58btcエンコードされたEd25519公開鍵>"
}
```

### トークンの発行

著者はタグサーバーに対して認証を行い、記事に対する署名済みトークンを発行してもらいます。認証方式およびトークン発行エンドポイントはこの仕様のスコープ外であり、各タグサーバーの実装に委ねます。

トークンは以下のJSONをEd25519で署名したものです。

```json
{
  "url": "https://blog.example.org/posts/ts-tips",
  "tag": "typescript",
  "server": "tag.example.com",
  "exp": "2026-06-09T00:00:00Z",
  "sig": "<base58btcエンコードされたEd25519署名>"
}
```

トークンは特定の `url` に束縛されており、別のページへの転用はできません。

### トークンのエンコード

URLクエリパラメーターとして渡すため、トークンJSONをbase58btcエンコードして使用します。

```
{url, tag, server, exp, sig} → JSONシリアライズ → base58btcエンコード → ?token=<値>
```

### トークンを使った登録

著者はエンコードされたトークンをタグリンクに含めます。

```html
<a href="https://tag.example.com/tag/typescript?url=https://blog.example.org/posts/ts-tips&token=<base58btcエンコードされたトークン>">#TypeScript</a>
```

リクエストを受信したタグサーバーは以下をすべて検証します。

1. トークンの署名が公開鍵で正しく検証できること
2. トークンの `url` が `url` クエリパラメーターと一致すること
3. トークンの有効期限が切れていないこと
4. バック検証でページにリンクが存在すること

すべて通過した場合にのみ、記事を登録します。

---

## 再検証

タグサーバーは、登録済みの記事を定期的に再クロールし、タグリンクが引き続き存在することを確認することを**推奨します**。
リンクが削除されていた場合、そのエントリは登録解除されます。

推奨間隔: 7日ごと

---

## 脅威モデル

| 脅威 | 対策 |
|---|---|
| `url` パラメーターの偽装 | バック検証: タグリンクが記事HTML内に存在することを確認 |
| リンクの一時的な設置・削除 | 定期的な再検証 |
| 登録後のコンテンツ差し替え | 定期的な再検証 |
| 正規ページからのスパム登録 | タグサーバー側のモデレーション (プロトコルの範囲外)|
| クローズドサーバーへの不正登録 | 特定URLに束縛された署名済みトークン |
| 意図しないタグの無断作成 | `tags` リストによる受け入れタグの明示的制限 |

---

## 設計思想

- **オプトインのみ** — 記事のタグ付けは著者の意図によってのみ成立し、第三者が勝手に行うことはできない
- **プラットフォームの協力不要** — タグリンクを含むページであれば、どんなサイトでも参加できる
- **ヘッドレスサーバー** — タグサーバーはAPIを公開するのみ。UIはアグリゲーターやクライアントに委ねる
- **段階的な信頼** — オープンサーバーはバック検証のみ、クローズドサーバーは署名済みトークンを追加
